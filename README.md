# Bát Tự — Tứ Trụ Mệnh Lý

A BaZi (Four Pillars of Destiny) application built on `bazi_db`, a SQLite database
extracted from an Android app. Cast a chart, save charts for yourself and family,
and read a daily interpretation written from the transit engine's findings.
Bilingual Vietnamese / English; light by default, dark on request.

```bash
cp .env.example .env      # then fill in AUTH_SECRET (npx auth secret)
docker compose up -d      # Postgres on :5433
npm install
npx prisma migrate deploy
npm run dev               # http://localhost:3100
```

| Script | What it does |
| --- | --- |
| `npm run gen:data` | Rebuild the data layer from `bazi_db`, printing the calendar audit |
| `npm run verify` | Replay the natal engine against all 54,787 DB rows, then check the transit engine |
| `npm run e2e` | Drive a running server through register → save chart → read day → journal |
| `npm run build` | Production build |

`gen:data` and `verify` need Node 22+ for `node:sqlite`. `e2e` expects a running
server (`npm run build && npm start`); point it elsewhere with `E2E_BASE_URL`.

The app runs on **:3100**, not Next's default :3000 — that port is taken on this
machine. Change it in the `dev` and `start` scripts if you need another.

## What came from the database, and what did not

`bazi_db` holds two very different kinds of content, and they are treated differently.

**The reference tables are used verbatim.** Stems, branches, hidden stems and their
order, the ten gods grid, the twelve life phases, branch and stem relationships,
seasonal strength, and the favourable/unfavourable element table are all copied
straight out and regenerated by `npm run gen:data`. This is the knowledge content and
it is sound.

**The calendar is computed instead.** The DB ships a 54,787-row day-per-row table
covering 1901-2050. Three things pushed us off it:

1. **It resolves solar terms only to a calendar day, in UTC+8.** A term is an instant
   in the Sun's orbit, not a date, and this site is meant to work from any longitude.
2. **It contains 22 terms that disagree with the Sun's actual position**, 14 of them
   unambiguously wrong by a day or two. Two are Li Chun — `1915-02-04` and
   `2004-02-03` — which means the *year pillar* is wrong for births around those
   dates. `npm run gen:data` prints the full list.
3. **It stops at 2050**, which is inside the lifetime of anyone born today.

So the calendar is derived from apparent solar longitude (Meeus ch. 25, with ΔT),
giving exact term instants for 1900-2100. The DB is kept as the oracle: `npm run verify`
replays every one of its rows through the engine, and the day pillar matches on all
54,787 of them.

The tradeoff is honest and stated in the UI: the solar model is good to about
±15 minutes, so a birth within an hour of a term boundary is flagged rather than
silently resolved.

### Size

The 2.4 MB database compresses to about 26 KB of generated TypeScript, because almost
all of the day table is redundant:

| Source | Compressed to |
| --- | --- |
| 54,787 day pillars | one anchor constant — the cycle never breaks |
| 150 year pillars | one formula — the year rolls at Li Chun |
| 1,800 month boundaries | 2,412 term instants, delta-encoded in base36 |

The whole engine is pure TypeScript with no native dependencies, so it runs in the
browser and the site builds to static files.

## Architecture

```
scripts/
  solar-longitude.mjs   apparent solar longitude + term instant solver
  extract-db.mjs        bazi_db -> src/lib/bazi/data/*.ts, with the calendar audit
  verify-engine.ts      159k assertions: DB replay, rule re-derivation, invariants
  verify-daily.ts       38k assertions on the transit layer
  e2e.mjs               browser smoke test of the signed-in flow

src/lib/bazi/
  data/                 GENERATED — do not edit
  calendar.ts           instants -> year / month / day / hour pillars
  solar.ts              civil clock -> local solar time
  analysis.ts           hidden stems, ten gods, phases, strength, relationships
  luck.ts               luck pillars (Đại Vận) and annual pillars (Lưu Niên)
  chart.ts              assembles a full chart
  daily.ts              transit layer: how one day meets a natal chart
  i18n.ts               VI / EN / 漢字 terminology

src/lib/reading/
  prompt.ts             system prompt (cached) + findings serialisation
  generate.ts           Claude call, with the template as the failure path
  template.ts           deterministic renderer — the floor, and the fallback
```

## How a daily reading is produced

The split that matters: **the rules engine decides what is true, and the prose
layer only decides how it is said.**

`buildDailySnapshot` takes a natal chart and a date and returns findings — the
day's pillar, its ten god, the twelve-phase position, every clash/harmony/
punishment against the four natal pillars, which elements the day brings, and
whether the chart wants them. Each finding carries a signed weight; the score is
their sum and the band is a threshold on it. Nothing here is generated.

`generateReading` hands those findings to Claude with a system prompt whose one
binding rule is *say only what the findings support*. The model is the writer,
not the analyst — it cannot introduce a clash that is not in the list.

Three things then guarantee a reading always exists and is always honest:

- **The template is the fallback, not an error page.** No API key, a refusal, a
  network failure, or a response that fails schema validation all land on
  `renderTemplate`, which states the same findings plainly.
- **The UI says which path wrote the text.** A template-rendered day is labelled
  as such rather than passed off as authored prose.
- **Prose is cached per profile per day per locale.** Switching language writes a
  second body against the same findings instead of recomputing the analysis.

The Claude call runs at `effort: 'low'` with the system prompt under a 1-hour
cache breakpoint — the analysis is already done, so there is little left to
reason about, and the prompt is identical for every user and every day.

## Accounts and data

Postgres via Prisma 7, Auth.js v5 with email/password and optional Google.

| Model | Holds |
| --- | --- |
| `Profile` | A saved birth record — the raw input, not the cast chart, so an engine fix reaches every existing profile on next render |
| `DailyReading` | Findings plus prose, keyed by profile and date; also the send-once record for the digest |
| `JournalEntry` | What the user says actually happened |
| `DayBookmark` | Good / hard / notable marks |
| `ViewHistory` | Which days were looked at |

Editing a profile's birth data deletes its cached readings, because they were
written against the old chart. Journal entries and marks survive.

The daily digest (`/api/cron/daily-digest`) is meant to be hit hourly with the
`CRON_SECRET` bearer token. It selects users whose chosen send-hour has just
arrived in their own zone, so one hourly cron serves every time zone. Writing the
reading row *is* the delivery record, which makes a retry within the same hour a
no-op rather than a second email.

### The time model

This is the part most worth understanding before changing anything.

- **Year and month pillars** are decided by comparing the *absolute birth instant*
  against solar-term instants. A term happens at the same moment everywhere on Earth,
  so these are correct from any time zone.
- **Day and hour pillars** follow *local solar time* at the birth longitude, because
  those cycles turn with the Sun overhead rather than with the civil clock. A birth at
  07:00 in western Spain — on Central European Time but sitting near 7°W — is at about
  05:30 solar time, two hour pillars earlier.
- **The late Zi hour** (23:00-24:00) takes the next day's stem while the day pillar
  stays on the current day, which is the convention the source DB encodes.

### Strength scoring

`analyseStrength` is a documented heuristic, not a canonical rule — classical texts
disagree, so the weights are stated in the code and surfaced in the UI: a visible stem
counts 1, a branch's main hidden stem 1.2, middle 0.5, residual 0.3, and the month
branch is doubled because the season commands the chart. The seasonal table from the DB
then shifts the result by up to ±15 points.

## Known limits

- **Historical time zones are not modelled.** A birth recorded under a wartime or
  pre-reform offset needs its UTC offset entered by hand.
- **Term precision is ±15 minutes.** Births near a boundary are flagged in the UI.
- **The strength weights are one school's, stated in code.** `analyseStrength`
  documents its numbers and the UI shows them; other traditions weigh differently.
- **The transit weights are the same kind of choice.** `W` in `daily.ts` encodes a
  plain reading of the classics, not a measured quantity. The band is coarse on
  purpose and the prose is told to hedge.
- **Nothing validates the readings against outcomes.** The journal exists so a user
  can check the readings against their own life; the app does not yet do that
  analysis for them. That comparison is the obvious next thing to build.
